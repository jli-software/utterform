The current interface already loads one `AppSettings` object plus input devices, local models,

The current backend already provides:

- OS-owned autostart state through `tauri-plugin-autostart`, read back after every requested change;
- single-instance and startup intents in `src-tauri/src/cli.rs` and `src-tauri/src/lib.rs`;
- responsive Settings modal, keyboard focus containment, compact-window tests and reduced-motion

## Product contract

Build a small, calm first-run assistant that can be completed in about one minute, excluding a
local-model download. It appears only when Utterform has never completed or skipped setup. It must
never interrupt an existing user merely because they upgraded to 0.8.0.

The assistant has four short steps:

1. transcription location and mode;
2. only the settings that apply to that mode;
3. shortcut and autostart;
4. a compact summary and explicit finish.

Every step shows a low-emphasis but always visible **Skip setup** action and the sentence:

> You can change all of this later in Settings.

**Skip is a complete, persistent skip.** One activation, without a confirmation dialog, closes
the assistant, marks onboarding complete and opens the normal main window. It discards every
wizard draft and must not save a typed API key, download a model, register a new shortcut, enable
autostart or apply any other choice from the assistant. It retains Utterform's shipped defaults,
including the existing default shortcut behavior. The assistant does not reappear automatically
on later launches after Skip; the user configures the app through normal Settings.

Do not perform external or durable setup work while the user is moving between steps. API-key
storage, model download, shortcut application and autostart changes begin only after **Finish
setup**. This is what makes Skip genuinely side-effect-free. While Finish work is in flight,
disable navigation, Skip and duplicate submission. A failed Finish keeps the assistant open with
an actionable error and a retry path; already completed Finish operations are detected and not
needlessly repeated.

### Step 1 — Choose where transcription runs

Heading: **How should Utterform transcribe?**

Present two primary cards with at most two short lines each:

- **Cloud — Recommended**
  - `GPT Transcribe` selected by default: best all-round accuracy; recorded audio is sent to
    OpenAI; an API key and network connection are required.
  - Offer `GPT Live Transcribe` as a secondary choice only where `live_support` says it is
    supported. State briefly that it types live at the cursor and supports Plain only. On an
    unsupported platform, omit it or show it disabled with the backend-provided explanation;
    never offer a choice that cannot run.
- **On this device**
  - `Local Whisper`: audio stays on the device and works offline after the model download.
  - State briefly that inference is CPU-based, is not Live Dictation, and speed depends on the
    device.

Write the choice directly into the existing `engine`/`cloud_model` draft mapping. Local Whisper
must retain the prior cloud-model choice exactly as the current main selector does, so switching
back later returns to it.

The assistant must not imply that every Local Whisper workflow is cloud-free: **Plain** needs no
API key and sends no text to OpenAI, but any other Action still uses the configured OpenAI text
model and sends the transcript for transformation. Keep this limitation to one short sentence.

### Step 2A — Cloud setup

Show this branch for GPT Transcribe or GPT Live Transcribe:

- an OpenAI API-key password field, initially empty even when a key is already present;
- key status (`Stored securely` or `Not configured`) from the existing key-presence command;
- a **Create API key** button that opens the fixed official URL in the system browser;
- one short note that the key stays in the operating-system keyring and cloud usage may be billed
  by OpenAI;
- **Languages**, accepting the existing comma-separated multiple language hints;
- **Vocabulary**, one expected name or term per line, with the existing `<`/`>` rejection rule;
- **Recording context**, a short optional free-text field.

These are exactly the inputs the current GPT Transcribe and GPT Live paths consume. Do not add a
parallel cloud settings type and do not expose unrelated text-model, reasoning-effort or Action
prompt controls in onboarding.

A cloud Finish requires either a key already stored or a non-empty key draft. Store a new key
only after Finish is pressed. Do not make a network request merely to validate the key: the
current app stores it locally and operational OpenAI requests own authentication failures.

### Step 2B — Local setup

Show this branch for Local Whisper:

- the backend-returned local-model cards, sizes and descriptions;
- `Whisper Base` selected by default and visibly marked **Recommended**;
- the existing concise trade-offs:
  - Tiny — fastest, for quick drafts;
  - Base — balanced, recommended for most devices;
  - Small — more accurate, but slower and more memory-intensive;
- whether each model is already downloaded;
- **Language**, using only the first non-empty language hint because local Whisper consumes one;
- **Vocabulary**, one expected name or term per line.

Do not show Recording context in the local branch; local Whisper does not consume it. Preserve any
previous cloud-only context in the underlying settings draft rather than erasing it, so switching
back to cloud later restores it.

Selecting an undownloaded model creates only a draft. Begin its existing checksummed download
after Finish, show the existing progress event in the assistant and remain on the summary until it
is ready. A downloaded model is reused. Failure leaves onboarding incomplete and offers Retry;
the `.part` cleanup and checksum behavior remain backend-owned. There is no promise that the
network transfer itself finishes within one minute.

### Step 3 — Quick access

Heading: **How should Utterform be ready?**

- Where global shortcuts are supported, show the existing enable switch and
  `ShortcutRecorder`, prefilled from the loaded setting or the backend default `Ctrl+Alt+D`.
  Explain in one line: press once to start, again to finish.
- Where shortcuts are unsupported, do not show a dead recorder. Show the backend-provided Wayland
  guidance for binding `utterform --toggle`.
- Show **Start Utterform when I sign in**, initialized from the operating system's actual
  autostart state. Default it to off when no entry exists. Explain in one line that it starts
  hidden in the tray.

Shortcut capture modifies only the wizard draft. Finish applies a changed shortcut through the
existing `apply_global_hotkey` command. A conflict returns to this step and keeps the chosen value
editable. Autostart remains OS-owned: call enable/disable only for a changed value, read the state
back afterwards, and believe the read-back rather than the request.

### Step 4 — Review and finish

Show only:

- transcription mode and selected local model or cloud key status;
- languages/vocabulary/context as counts or `Configured`, never echo sensitive free text;
- shortcut state or the Wayland command;
- autostart state;
- **Back**, **Skip setup** and **Finish setup**.

After a successful Finish, close the assistant and show the normal main window with a brief
`Setup complete` status. Do not start a recording automatically and do not replay a startup or
single-instance recording intent that arrived while setup was incomplete.

## Explicitly out of scope

Keep the one-minute promise by leaving these in normal Settings:

- microphone selection and sound testing;
- Theme and other appearance controls;
- text model, reasoning effort and Action prompt editing;
- output directory, typing method/delay and history controls;
- API-key verification calls, account creation, billing setup or embedded web content;
- a new telemetry, analytics or account system;
- GPU local inference or additional local models;
- release, updater or packaging behavior changes.

The shipped defaults remain in force for omitted fields, especially Clipboard output, system
theme, history and recording sounds.

## State, migration and startup invariants

### One authoritative completion flag

Add `onboarding_completed: boolean` to the shared TypeScript/Rust settings schema.

- `AppSettings::default()` and `DEFAULT_SETTINGS` use `false` for a genuinely new installation.
- A stored pre-0.8 settings JSON that lacks the field deserializes it as `true`. This migration is
  required so an upgrade never launches onboarding for an existing user.
- A stored explicit `false` survives save/reload and keeps onboarding active after a failed or
  abandoned Finish.
- Skip and successful Finish save `true` atomically through the existing settings writer.

Implement the legacy default explicitly rather than changing the meaning of every other
`#[serde(default)]` field. Add tests proving all three cases: no settings file, old settings file
without the field, and new file with explicit false/true.

### Side-effect ordering

Before Finish, the assistant is a pure draft. On Finish:

1. save the chosen settings with `onboarding_completed = false`, so a crash or restart resumes;
2. store a newly entered API key when the chosen path requires it;
3. download the selected local model when required and wait for verified activation;
4. apply a changed global shortcut and surface a reservation conflict on Step 3;
5. apply a changed autostart value and verify it by reading the OS state back;
6. save the same settings with `onboarding_completed = true`;
7. enter the main UI without replaying old recording intents.

Each step is idempotent. If a later operation fails, prior successful operations may remain (for
example a securely stored key or downloaded model), but the completion flag stays false and the
next launch resumes setup using the actual key/model/autostart state. Do not attempt a misleading
cross-system rollback.

Skip follows a different path: discard the wizard draft and save the originally loaded settings
with only `onboarding_completed = true`. It must not run steps 2–5 above.

### Startup and single-instance behavior

Today only the `Show` intent reveals the window, while Toggle/Start deliberately preserve focus
for dictation. Incomplete onboarding changes that boundary:

- native setup must reveal the main window when onboarding is incomplete, even when the first
  process was launched by Toggle/Start or a stale autostart entry;
- the frontend consumes and discards a pending recording intent while onboarding is active;
- a second-instance Toggle/Start/Stop/Cancel received during onboarding reveals the assistant and
  is consumed, never queued for later;
- completed/skipped users retain the existing focus-preserving intent behavior unchanged;
- autostart for a completed user remains silent and hidden.

Use one shared native `needs_onboarding` decision derived from loaded settings for startup reveal
and intent routing. Do not create a parallel frontend-only guess from settings-file existence.
Settings load failure keeps the existing error behavior; it must not silently overwrite a damaged
file or convert corruption into a new-user flow.

## UI architecture

Prefer extracting the assistant from `App.svelte` into a focused component such as
`src/lib/OnboardingAssistant.svelte`, with typed draft/result data and callbacks owned by
`App.svelte`. Reuse:

- `SelectMenu.svelte` and `ShortcutRecorder.svelte`;
- the existing `modalFocus` action and accessible dialog semantics;
- the current transcription-mode mapping instead of duplicating it in two components;
- current model progress events and model formatting;
- current autostart read-back and hotkey suspension/application behavior.

The assistant is visually smaller than Settings: one main decision per screen, short copy, no
left navigation rail and no long scrolling form at normal desktop sizes. It must still fit the
existing 360 × 400 compact-window contract with its header, progress (`1 of 4`), content and
footer actions reachable without horizontal overflow. Honor light/dark/system themes and
`prefers-reduced-motion`.

Keyboard and accessibility requirements:

- initial focus lands on the step heading or first choice;
- Tab order follows visible controls; hidden branch controls are not focusable;
- Back/Next/Finish/Skip have stable accessible names;
- Enter activates the focused primary action but never skips implicitly;
- Escape does not silently mark setup skipped; Skip is explicit;
- progress, model-download state and errors are announced through appropriate live regions;
- the assistant remains a modal barrier: main-window shortcuts and recording buttons do not act
  beneath it.

## Native API and external-link boundary

`tauri-plugin-opener` is intentionally registered with `open_js_links_on_click(false)` and the
WebView has no broad opener capability. Preserve that boundary. Add a no-argument native command,
for example `open_openai_api_keys`, that opens only the compiled-in
`https://platform.openai.com/api-keys` URL through the plugin's Rust API. The frontend must not
send a URL or path. Log failure once at the native owner and return a concise referenced error to
the assistant.

Do not add JavaScript opener permissions, generic `open_url(url)` IPC or an embedded browser.

## Diagnostics and privacy

Follow the repository-wide diagnostics invariant. Add stable, low-volume lifecycle events such
as:

- `onboarding.shown` with source (`first_launch`, `startup_intent`, `second_instance`);
- `onboarding.skipped`;
- `onboarding.finish_started` and `onboarding.completed` with engine/model identifiers and boolean
  feature states only;
- `onboarding.finish_failed` with the owning stage and existing failure reference.

Never log the API key, language values, vocabulary, recording context, shortcut keystrokes while
capturing, full settings JSON or any typed draft. Model id, engine, cloud mode, counts and boolean
states are acceptable metadata. Existing settings/key/model/hotkey/autostart commands remain the
owners of their operational events; avoid duplicate error records.

## Automated validation

### Rust

- genuinely absent settings produce `onboarding_completed = false`;
- legacy settings without the field produce `true` and preserve all existing values;
- explicit false/true survive atomic save and reload, including backup recovery;
- incomplete onboarding reveals for every startup intent and completed onboarding preserves the
  existing intent matrix;
- recording intents received while incomplete are consumed once and never replayed;
- the fixed-link command accepts no URL argument and maps opener failure to one diagnostic event;
- existing hotkey, CLI, settings, model and diagnostics tests remain green.

### Svelte/Vitest

- new install opens Step 1; completed/legacy settings never open the assistant;
- Skip is reachable on every step, calls no key/model/hotkey/autostart mutation, preserves loaded
  values and saves only completion;
- Cloud defaults to GPT Transcribe, requires a stored or entered key, and shows languages,
  vocabulary and context;
- GPT Live appears only when supported and shows its Plain/platform limitation;
- Local defaults to Base, shows backend descriptions/sizes, one language plus vocabulary, hides
  context and does not require a key for Plain;
- switching branches preserves inactive branch values without showing unsupported controls;
- no external/durable operation runs before Finish;
- Finish serializes key, model, hotkey, autostart and final completion; duplicate clicks cannot
  overtake it;
- each failure returns to the owning control, remains retryable and leaves completion false;
- startup and second-instance recording intents cannot pass through the modal;
- fixed API-key link success/failure and model progress are accessible;
- focus containment, keyboard navigation, Escape behavior and teardown have no leaked listeners.

## Definition of done

- A genuinely new user sees a small four-step assistant and can reach the normal app in about one
  minute, excluding an explicitly chosen model download.
- **Skip setup** is visible on every step, requires one activation, applies none of the wizard
  drafts and prevents the assistant from appearing again automatically.
- Existing 0.7.x users upgrade without seeing onboarding or losing any setting, key, model,
  shortcut or autostart state.
- Cloud and Local branches show only supported settings and state their privacy, API-key,
  performance and Action limitations briefly and accurately.
- Every screen says the choices remain changeable in Settings.
- Finish is ordered, retryable and crash-safe; completion is never recorded before required
  side effects are confirmed.
- No recording intent can bypass or outlive incomplete onboarding.
- The API-key page opens through one fixed native command without broad WebView opener permission.
- Automated checks and explicitly claimed native/manual checks pass on the exact reviewed commit.
- No merge, release, deployment or automatic upload occurs as part of implementation.

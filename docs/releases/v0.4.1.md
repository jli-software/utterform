# Utterform 0.4.1 — The dictation key on Windows, and text that arrives whole

0.4.0 made dictation work from anywhere on Omarchy, through a Hyprland binding. This patch gives Windows and macOS the same thing without a compositor config, and fixes the text arriving with letters missing.

## A dictation key on Windows and macOS

Windows, macOS and X11 let an application reserve a key combination for itself. Utterform now does, so what `bind = SUPER, D, exec, utterform --toggle` gives on Omarchy is available on those platforms out of the box:

**Ctrl+Alt+D** — press it anywhere to start recording, press it again to finish.

The window never comes forward. You keep typing where you were; the text lands there when it is ready. The sounds are the confirmation, because there is nothing to look at: a click when recording starts, a click when it stops, and the completion chime once the text has actually been transformed and delivered.

Change the key, or turn it off, under **Settings → Dictation key**. A key another application already holds is reported where you entered it rather than failing silently.

Wayland is deliberately left out. The compositor owns the keyboard there and gives no application a global shortcut, so a Wayland session shows what to bind instead and keeps using `utterform --toggle`. Nothing about the Omarchy setup changes.

## Typing at the cursor no longer drops letters

Typing the finished text into a terminal could lose characters — "Session" arriving as "ession". The transcription was correct; the delivery was not. Synthesized keystrokes travel one character at a time through the compositor, the input method and the receiving application, and each of them can drop or reorder one when input arrives faster than a person could type.

**Typing at the cursor now pastes by default.** The whole text moves in one step, so there is nothing to reorder — terminals included. Utterform picks the paste a terminal actually listens for (`Ctrl+Shift+V`) and the one every other window does (`Ctrl+V`). When Clipboard output is already on, the transcript is on the clipboard anyway and the paste costs nothing extra; when it is off, paste delivery leaves the text there.

**Keystrokes remain available** under **Settings → Typing at the cursor**, for windows that refuse a paste, and they are more reliable than they were:

- a Shift press and release before the text, because some Wayland clients swallow the first character a newly created virtual keyboard sends,
- a delay between keystrokes, 15 ms by default and adjustable to 500 ms, because input faster than a human types is exactly what gets reordered.

On Windows this is not a trade-off at all: `SendInput` appends the whole batch to the input queue in one call, so both methods deliver the text intact.

## Typing at the cursor now works on Windows

**Type** in the output bar was Linux-only. It now works on Windows too, through `SendInput`, with no helper program to install. Characters go in as Unicode rather than as scan codes, so the transcript does not depend on the active keyboard layout, and every line break arrives as a real Return.

Windows refuses input from a normal process to a window running as administrator; that case is reported as a delivery warning instead of an empty text field. macOS typing at the cursor is still not implemented.

## Upgrading

Existing settings carry over. An installation that has never seen these options gets the dictation key on `Ctrl+Alt+D` and paste delivery; both are in Settings.

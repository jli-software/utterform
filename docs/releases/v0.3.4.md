# Utterform 0.3.4 — GPT Transcribe works again

## Fixed: GPT Transcribe hung forever in 0.3.3

0.3.3 broke transcription through OpenAI. Recording and stopping worked, then the app stayed on "Transcribing with GPT Transcribe…" and never finished. Local Whisper was unaffected.

The cause was a Cargo feature, not the tray code itself. The Linux tray added in 0.3.3 pulled in `ksni` with its `tokio` feature, and Cargo unifies features across the whole build, so `zbus` was compiled with `tokio` too. `zbus`' blocking API then drives a tokio runtime instead of parking the thread — and the OS keyring reads the API key through exactly that blocking API, from inside Tauri's async runtime. Tokio refuses to start a runtime inside a runtime and panics, the command never returns an answer, and the interface waits forever.

Local Whisper never reads the key on that path, which is why only OpenAI was affected.

Utterform now builds `ksni` on `async-io` instead. A test reads the keyring from inside an async runtime and fails if any dependency reintroduces the conflict.

## Long recordings

The OpenAI request had a two-minute cap covering upload and transcription together. A ten-minute recording is roughly a 19 MB upload, which could exceed it on a normal connection. Utterform now bounds inactivity — two minutes without data — and allows the exchange itself to take up to fifteen minutes.

The ten-minute recording limit is unchanged. Longer recordings are a separate piece of work: the OpenAI endpoint accepts at most 25 MB, which this format reaches at about 13 minutes.

## Verified

`tray::status_notifier_item::tests::a_left_click_reaches_the_application` and the new `secrets::tests::the_keyring_can_be_reached_from_the_async_runtime` both run in CI. The keyring test reproduces the 0.3.3 failure exactly — it panics with "Cannot start a runtime from within a runtime" against the 0.3.3 dependency set and passes with this one.

Not verified here: an actual transcription against the OpenAI API, which needs a key and a microphone.
